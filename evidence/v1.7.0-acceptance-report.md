# agentgateway v1.7.0 隔离验收报告

时间一律用亚洲/新加坡（UTC+8）。本报告只记录本轮在隔离虚拟机上的实测。公开 issue 与公告只作为核对清单，不事先当成已经复现。

建议：**继续作为代理与策略对照候选**。放弃把它当成独立 agent 的任务控制台、持久任务台、只出站队列，或跨公司业务隔离产品。本次验收没有新增付费授权，也没有公网部署。

能证明的只有：官方 v1.7.0 standalone 进程，在本机回环上，把虚构公司 A/B 的确定性 A2A 请求转到两个独立合成进程，并带回这两个进程的真实状态。网关自己没有任务库。

## 启动步骤

1. 下载官方二进制并核对 sha256。
2. `agentgateway-linux-amd64 --version`，确认版本与 `26f5aebe…`。
3. 在临时目录生成测试用 ES256 密钥与 JWKS，以及两份互不相同的后端凭据文件。这些材料不进入 git。
4. 配置要点：
   - `config.adminAddr: 127.0.0.1:15000`
   - `config.statsAddr` 与 `config.readinessAddr` 设为 `off`
   - `config.session.key: disabled`（见下方会话密钥观察）
   - 两个 gateway 都设 `bindAddress: 127.0.0.1`（数据面 18080，MCP 18083）
   - 公司路由使用 `jwtAuth.mode: strict`、按 `jwt.org` 的 `authorization.require`、`a2a: {}`、各自的 `backendAuth` 文件凭据，以及把路径前缀写回 `/`
5. 先起两个合成 A2A 进程，再执行 `agentgateway-linux-amd64 -f <临时配置>`。
6. 任务文本固定为 `GIT1-TEST-001`。没有模型调用。

公司 A 的合成进程支持 `tasks/cancel`。公司 B 的合成进程对取消返回 JSON-RPC `-32601`，并继续执行。两边都要求自己的后端凭据，不接受对方的凭据，也不接受客户端 JWT。

## 合成闭环：PASS（只证明代理层）

两个后端是网关之外的独立进程。网关没有替它们生成结果。

| 时间 (+08) | 动作 | 结果 |
| --- | --- | --- |
| 12:06:39 | A，`A2A-Version: 1.0`，`message/send` | HTTP 200，`task-a-1`，`ctx-a-1`，状态 `completed`，正文 `GIT1-TEST-001`。响应是 v1.0 嵌套的 `result.task` |
| 12:06:39 | A，`tasks/get` 同一 task | HTTP 200，状态与正文与上面一致 |
| 12:06:39 | A，`A2A-Version: 0.3`，`tasks/send` | HTTP 200，`task-a-2`，`ctx-a-2`，`kind=task`，状态 `completed`，正文 `GIT1-TEST-001` |
| 12:06:39 | A，`tasks/get`（0.3） | 与 `task-a-2` 一致 |
| 12:06:39 | B，`message/send` | HTTP 200，`task-b-1`，`ctx-b-1`，`completed`，正文 `GIT1-TEST-001` |

后端计数：A 创建 6 个任务、执行 6 次；B 创建 3 个任务、执行 3 次。访问日志把 v1.0 嵌套结果和 v0.3 扁平结果都记成 `a2a.result.kind=task`、`a2a.task.state=completed`，并带上 `a2a.context.id`。

成功请求的日志字段示例（已去掉源端口）：`jwt.sub=user-a`，`company=company-a`，`protocol=a2a`，`a2a.method=message/send`，`a2a.response.outcome=success`，`a2a.context.id=ctx-a-1`，`endpoint=127.0.0.1:18081`。日志里没有 task id。

### 0.3 / 1.0、卡片路径、签名与 SDK 绕行

卡片请求都是 HTTP 200。

- `/.well-known/agent.json`：顶层 `url` 被改写成网关地址，例如 `http://127.0.0.1:18080/tenant-a`。
- `/.well-known/agent-card.json`：`supportedInterfaces[].url` 被改写，JSON-RPC 与 `/rest` 两条都落到网关前缀下。
- `provider.url` 与 `documentationUrl` 仍是后端私网地址（`127.0.0.1:18081` 或 `18082`）。重写不完整。
- 卡片里的测试签名字节与重写前相同。重写后的卡片验签失败；直接向后端读取的原卡片验签成功。网关没有去掉签名，也没有重新签名。
- 后端记录到转发来的 `A2A-Version: 1.0` 与 `0.3`。访问日志没有版本字段。两个版本都没有被拒绝，也没有版本协商。
- 补充探针：请求 `Content-Type: application/a2a+json` 被原样转到后端并返回 HTTP 200，但网关日志是 `unknown content type from A2A`，`a2a.method=unknown`。响应体仍是 JSON，所以 `a2a.response.outcome` 仍被填上。这不是该内容类型的方法识别。
- gRPC binding、完整 HTTP+JSON binding、官方 SDK 互操作套件：未测。
- 已知后端地址时，带该后端自己的凭据直接请求 `http://127.0.0.1:18081/.well-known/agent-card.json` 得到原始 URL 与仍然有效的签名。这条路径不经过网关策略。

因此不能把 v1.7.0 写成 A2A 全协议认证。这与仍开放的 [#2701](https://github.com/agentgateway/agentgateway/issues/2701) 所描述的边界一致；上面是 v1.7.0 二进制上的实测，不是把 issue 正文当成结果。

### 这一层明确没有的能力

- 没有持久化任务台。任务只活在合成进程内存里。网关重启后，`tasks/get` 仍能读到后端还保存的 `task-b-1`。
- 没有出站任务队列。后端端口关闭时，网关约 2.5 ms 返回 HTTP 503，正文 `connection refused`，日志 `UpstreamFailure`。后端重新监听后，同一次 `tasks/get` 恢复为 HTTP 200。
- 没有租户业务 UI，没有 A2A 派发、状态或取消页面。
- 只出站、由 agent 自己来拉任务的模式：本版本这次没有可用实现，标 **未测**。`examples/netbird-agent-network` 依赖外部网络和 LLM 密钥，未启用。
- 不需要域名、公网服务或新增费用，才能完成本地回环验收。网关必须能主动连接配置里的后端 URL；后端不可达时请求失败，不会排队。

## 隔离安全：FAIL

路由身份这一层是通过的。要求的 fail-closed 限流和卡片私网地址没有通过，所以整项为 FAIL。

### 通过的部分：JWT 路由与双层凭据

正式配置把 `jwtAuth.mode` 设为 `strict`。

| 用例 | 结果 |
| --- | --- |
| A 的 token 访问 B 的路由 / task / 卡片 | HTTP 403，`authorization failed`。日志 `reason=Authorization`，`jwt.sub=user-a`，`company=company-a` |
| 在 A 的路由上篡改 `x-tenant` / `x-org` 后再访问 B | 仍是 HTTP 403 |
| 无 token | HTTP 401，`authentication failed` |
| 过期 token | HTTP 401。日志 `reason=JwtAuth`，`ExpiredSignature` |
| B 的 token 读取 A 的 agent card | HTTP 403 |

另一次启动没有写 `mode`。那次无 token 是 HTTP 403 `authorization failed`，过期 token 仍是 401。源码枚举把 `Optional` 标成默认值，并写明这样会放行没有 JWT 的请求。正式结论以 `strict` 那次为准：缺凭据和过期凭据都是 401。

A 拿着 A 的 token，在 A 的路由上查询 B 的 `task-b-1`：HTTP 200，JSON-RPC `-32001`，`task not found`。网关没有按 task id 做租户判断。隔离来自两条独立后端；A 的进程里没有 B 的任务。若两个公司共用一个后端，这一层不会挡住 task id。

双层凭据：

- 直接访问 A，不带后端凭据：401
- 直接访问 A，带 B 的后端凭据：401
- 直接访问 A，带 A 的后端凭据：200
- 经网关访问时，客户端 JWT 没有出现在后端的 `Authorization` 上（A 的 `clientAuthorizationPresent=0`）
- 客户端自行塞入错误的后端凭据头后，网关仍用 A 自己的凭据完成 `tasks/get`，返回 `task-a-1`
- 两份后端凭据不同，没有共用一把上游超级密钥

### 未通过：#3523 描述符错误没有 fail-closed

[#3523](https://github.com/agentgateway/agentgateway/issues/3523) 在查询时仍是 open。本轮不抄配置配方，只记 v1.7.0 的结果。同一 `failureMode: failClosed`，限流服务地址不可连接：

- 描述符可以求值时：HTTP 500，正文 `rate limit failed`。服务失败这条是关闭的。
- 身份描述符因缺少 JWT 上下文而无法求值时：请求到达合成后端，HTTP 200。
- 描述符字面量可以求值、但 cost 表达式无法求值时：同样到达后端，HTTP 200。

本地 `localRateLimit` 对照：无法求值的 key 与固定 key 都是第一次 HTTP 200、第二次 HTTP 429。本地桶没有因为 key 失败而跳过。跳过发生在远程描述符组装。

这不满足“描述符错误应 fail-closed”。

### 未通过：卡片把后端私网地址交给调用方

见合成闭环。调用方收到的 agent card 仍含 `127.0.0.1:18081` 或 `18082`。主 URL 已指向网关，其他 URL 字段没有。

### 密钥与地址

- 标准输出访问日志、OTLP 导出（16241 字节，1 次）、SQLite 文件、`/config_dump`（26046 字节）都没有测试 JWT、后端凭据或私钥。
- 访问日志和 trace 含 `endpoint=127.0.0.1:18081/18082`。`/config_dump` 含后端端口。管理面只在回环上，但这不是“日志和配置里没有私网地址”。
- 第一次把 `session.key` 留空且配置文件可写时，进程把生成的会话密钥写回配置文件，并带有自动生成说明。正式测量改为 `session.key: disabled` 后，文件和 config dump 都没有这把密钥。密钥值不写入本报告。
- `request_logs` 与 `request_log_payloads` 在退出时都是 0 行。`POST /api/logs/search` 返回 `{"logs":[],"nextCursor":null}`。
- 访问日志能把一次请求连到 `jwt.sub`、自定义 `company`、路由、`a2a.method`、结果种类、任务状态和 `a2a.context.id`。它没有 task id。SSE 流日志只有 `a2a.method=message/stream` 和 HTTP 200，没有 outcome、任务状态或 context id。这不能当作完整业务审计。

管理面无登录。绑定在 `127.0.0.1:15000` 时，本机用户可以直接打开。这符合项目把管理接口视为本机特权面的说法；它不是远程多租户控制面。

## 故障恢复：PASS（只证明代理层）

网关返回的是传输和协议结果。任务是否还在跑，以合成进程内存为准。

| 场景 | 调用方 / 日志 | 后端实际动作 |
| --- | --- | --- |
| 下游超时。`requestTimeout: 1s`，后端延迟 3 秒才回写 | 12:06:43，HTTP 504，`request timeout`，耗时 1001.6 ms。日志 `a2a.method=message/send`，`reason=Timeout`，没有 outcome | 执行次数由 3 增到 4。`task-a-4` 随后在后端变为 `completed`，正文 `GIT1-TEST-001`。网关超时没有停止执行 |
| 客户端读到第一条 SSE（`working`）后断开。`task-a-5` | 日志最终仍是 HTTP 200，`a2a.method=message/stream`，时长 6115 ms，没有任务状态 | 断开后约 0.4 秒仍是 `working`。保持时间结束后为 `completed`。`transportClosed=false`，`cancelRequested=false`。下游断开没有变成上游断连，也没有变成取消 |
| A 支持取消。`task-a-6` | `tasks/cancel` HTTP 200，状态 `canceled`。日志 `a2a.task.state=canceled`，`outcome=success` | `cancelRequested=true`，worker 已停，没有结果正文 |
| B 不支持取消。`task-b-2` | HTTP 200，JSON-RPC `-32601`，`tasks/cancel is not supported`。日志 `outcome=error`，`error_code=-32601` | 任务继续跑完，状态 `completed`，正文 `GIT1-TEST-001`。网关没有把“不支持”显示成已取消 |
| HTTP 200 包裹 JSON-RPC 错误 | HTTP 200，错误码 `-32602`。日志 `outcome=error`，`error_code=-32602` | `jsonRpcError` 计数 +1，没有因此多一个完成任务 |
| 只杀网关进程 | 数据面端口关闭，进程信号 -9。B 的端口仍在 | `task-b-3` 在杀进程后约 2 秒和约 10 秒都仍是 `working`，`workerStopped=false`，`cancelRequested=false`。此时 `transportClosed=true`，因为网关进程消失把上游连接拆掉了。执行没有停 |
| 网关再次启动 | 101.1 ms 后可连接 | `tasks/get task-b-1` 仍是后端里的 `completed` / `GIT1-TEST-001` |
| 操作员电脑睡眠、关机、断网 | **未测** | 网关和两个 agent 都在这台虚拟机上。没有常驻中继。整机睡眠或关机会同时停掉它们；本轮没有实际做这个动作 |

传输终止、取消请求、实际停止是三件不同的事：

- 客户端提前关闭 SSE：后端继续执行并完成。
- `tasks/cancel`：只有声明支持的 peer 停工；不支持的 peer 返回错误并完成。
- 只结束网关进程：后端连接被拆开，任务循环仍继续。

管理页没有把 HTTP 200 里的 JSON-RPC 错误画成一条失败任务。调用方必须读正文；访问日志会把 outcome 标成 `error`，同时保留 HTTP 200。

## 本地管理端与远程控制

本地页面能打开。Headless Chrome 打开 `http://127.0.0.1:15000/ui`，页面标题为 agentgateway，侧栏版本 **1.7.0**，旁边的修订号是 `26f5aebe99a36a037fe54f8080a608aca5547e15`。

首页是 Gateway Overview，分区为 LLM、MCP、Traffic。导航是 Home、LLM、MCP（Servers、Policies、Tool Playground）、Traffic（Gateways、Routes）、Tools（CEL Playground、Raw Configuration）、Settings。页面语言是英文。截图：`evidence/ui-admin-home.png`。

前端资源里没有 “Cancel task”、`tasks/cancel` 或 “Agent Card” 导航。`A2A` 字符串出现在内嵌配置 schema 的说明里。Tool Playground 属于 MCP。

所以：

- 本地页能亮，并能看见网关、路由和 MCP 目标。
- 不能在这个页面上派发、查询或取消一个独立 A2A agent。
- 这不是对一台远程独立 agent 的控制面。
- 不适合零基础用户。使用者需要会写 YAML、JWT、CEL 和后端凭据。

## 建议

继续把 v1.7.0 standalone 当作 **代理 / 策略对照**：JWT 路由、每后端独立凭据、A2A JSON 透传、卡片主 URL 重写、访问日志里的方法与 context id，都有实测。

- 零基础用户的 agent 控制台
